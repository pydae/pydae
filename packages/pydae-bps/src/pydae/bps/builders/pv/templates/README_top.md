# __NAME__ — protocol benchmark suite

Auto-generated by ``pydae.bps.builders.pv_designer``. Parallel
co-simulations of the **__NAME__** plant (__M__ feeder(s) × __N__ inverter(s)
per feeder = __MN__ inverters total) — one per SCADA stack supported
by ``colinker``, plus a no-Mininet ``local`` case. Same electrical model,
same PI control law, same step magnitudes. Only the wire layer changes.

## Layout

```
__NAME__/
├── modbus/    # pymodbus 3.13
├── iec104/    # c104 v2.2.x  (M_ME_NC_1 / C_SE_NC_1)
├── dnp3/      # in-tree pure-Python codec, AI G30v5 / AO G41v3
├── dds/       # cyclonedds  (OpenFMB-style profiles)
└── local/     # direct pydae HTTP — pydae_ppc, no Mininet, no wire stack
```

Each subdir carries `__NAME__.json` and a stack-specific `README.md`. The four
protocol folders carry `run.py` (Mininet cosim); `local/` carries `run.sh`
(pydae_sim + pydae_ppc). **All** stacks carry the structured `tests/` suite
(`open_loop_step`, `closed_loop_step`, `frequency_response`, plus `mitm_attack`
on some); shared comparison tooling and cross-protocol outputs live in
`common/`.

## Workflow (any protocol)

```bash
# Terminal A — launch the cosim (stays attached to mininet>)
cd <protocol>/
sudo python3 run.py
```

Wait for the topology banner `PPC API (macOS): http://localhost:8090/`.

```bash
# Terminal B — drive the step, record, plot (every stack carries tests/)
cd <protocol>/  && PY=/home/jmmmacubu/miniforge3/envs/pydae_dev/bin/python3 \
                && $PY tests/closed_loop_step/run.py
```

Tear down: `exit` at the `mininet>` prompt in Terminal A.

## Run everything (automated)

`common/run_all_tests.py` drives the whole matrix — every test for every
protocol and `local` — in one shot. For each stack it cleans up any prior
cosim, launches it, waits for the PPC API **and a live ground-truth feed**,
runs the suite, then tears the cosim down before the next one.

```bash
cd __NAME___wecc

# All five stacks (modbus iec104 dnp3 dds local):
sudo python3 common/run_all_tests.py

# Only a subset:
sudo python3 common/run_all_tests.py iec104 dds

# Skip the MITM phase (functional tests only):
sudo python3 common/run_all_tests.py --no-mitm
```

It **must** run as root (Mininet needs it), but the test drivers and plotting
run as the invoking user (via `sudo -u $SUDO_USER`), so outputs are not
root-owned. Per stack it runs `open_loop_step → closed_loop_step →
frequency_response` (modes `p`, `q`, `pq90`), then at the end regenerates the
comparison plots and the metrics table.

For the four **networked** stacks it then runs the **stealthy over-power MITM**
(`mitm_attack`) as a proper test call. The plant is parked at its **12 MW cap**
with **feedforward off** (so the PI integral is free to wind), the cosim is
relaunched in `--mitm-serve` mode — an **idle** MITM proxy that does nothing
until armed — and the `mitm_attack/run.py` driver then **arms → records →
disarms** itself via a control file (`/tmp/colinker_mitm_<proto>.ctl`): a clean
baseline, then the POI readback is biased **low** (`offset_frac = -0.0909`, so
`spoofed = real × 0.909`). The controller drives the falsified reading to the
12 MW target, so the **real plant is pushed to `12 / 0.909 ≈ 13.2 MW — +10 % over
the cap`**, well under the 15 MW plant limit so there is **no saturation or
alarm**. Then recovery. `local` has no wire layer, so it is skipped; disable the
phase with `--no-mitm`.

> **Why feedforward off:** under feedforward the `ff_i_band` freeze stalls the
> integral on the large spoofed error, so the plant would stay pinned at 12 MW
> and the attack would only produce a *lying meter* — not real over-power. Pure
> PI lets the integral wind the real plant past the cap. Tune the breach with
> `--offset-frac` / `--cap-mw` on the driver, or `MITM_OVERPOWER` / `MITM_CAP_MW`
> in `common/run_all_tests.py`.

> The serve cosim is separate from the clean suite because `--mitm-serve` uses
> the deterministic explicit-redirect path (POI routed through the transparent
> proxy), which would otherwise perturb the latency benchmarks. The *over-power*
> fixed-spoof variant (`{"armed": true, "value_mw": …}`, or `run.py --mitm
> --mitm-value-mw …`) rails the PI to saturation — not run automatically; see
> `tests/mitm_attack/README.md`.

**Network capture:** the MITM phase records the wire traffic for the whole
serve session (baseline → armed → recovery) so the attack is visible on the
*communication* side, not just the power side. tcpdump runs in the **PPC**,
**POI** and **MITM** namespaces and writes `<proto>/tests/mitm_attack/pcap/{PPC,
POI,MITM}.pcap` (chowned back to you afterwards). The three vantage points show
the attack signature: the POI sends the true value, the MITM host rewrites it,
and the PPC receives the falsified one — same transaction id / topic, different
payload bytes. Filters: Modbus tcp/502, IEC 104 tcp/2404, DNP3 tcp/20000, DDS
UDP/RTPS (plus ARP). Inspect with e.g.:
```bash
tshark -r modbus/tests/mitm_attack/pcap/PPC.pcap  -Y modbus       # PPC's view
tshark -r modbus/tests/mitm_attack/pcap/MITM.pcap -Y modbus       # the rewrite point
```

**Run just the MITM phase** (skip the functional suite + plots):
```bash
sudo python3 common/run_all_tests.py --only-mitm            # all four networked stacks
sudo python3 common/run_all_tests.py modbus --only-mitm     # one stack
```

**MITM as a manual test call:** on any networked stack you can drive the attack
against a single running cosim without a relaunch per attack (add `--pcap-dir`
to capture traffic):
```bash
cd <protocol>/ && sudo python3 run.py --no-cli --mitm-serve \
     --pcap-dir tests/mitm_attack/pcap        # Terminal A
$PY tests/mitm_attack/run.py                  # Terminal B: arm→record→disarm
```

- **Runtime:** ~45–60 min for the full sweep (each stack ≈ 9–10 min: model
  build + 5 tests + teardown).
- **Logs:** `common/run_logs/summary.txt` (per-test OK/FAIL) plus
  `common/run_logs/<proto>_{cosim,tests}.log`.
- **Robustness:** one stack failing doesn't abort the rest. If a stack's
  ground-truth feed is frozen it is skipped and flagged (restart that cosim and
  re-run just that stack, e.g. `sudo python3 common/run_all_tests.py dds`).

## Modifying parameters

**Controller gains, limits, control period, feedforward band** — edit the
`ppc` section of each stack's `__NAME__.json`. These load when the cosim
starts, so **restart the cosim** for a change to take effect. Current values
are tabulated in `common/ppc_parameters.md`.

```jsonc
// <protocol>/__NAME__.json  →  "ppc": { ... }
"K_pp": 0.1, "K_ip": 0.35,          // active-power PI gains
"K_pq": 0.1, "K_iq": 0.35,          // reactive PI gains
"ctrl_dt_s": 0.1,                   // control period (per-stack: comms speed)
"p_min_mw": 0.0, "p_max_mw": 1.0,   // per-inverter active clamp
"q_min_mvar": -0.5, "q_max_mvar": 0.5,
"ff_i_band_mw": 0.2, "ff_i_band_mvar": 0.15  // integral freeze band under feedforward
```

The gains are intentionally **shared across stacks** so the comparison isolates
the wire layer; only `ctrl_dt_s` differs, set by how fast each transport can
close the loop (0.1 s local/modbus/dds, 0.5 s dnp3, 1.0 s iec104 — iec104 is
unstable faster, see `iec104/iec104_saturation.md`).

**Step magnitudes / timing** — the step tests pre-settle at P=2 MW, then step
P 2→3 MW and Q 0→1 Mvar. Change these in the relevant
`<protocol>/tests/<test>/run.py` (`drive_pq_step(p_initial=…, p_step=…,
q_step=…, t_end=…)`). The `closed_loop_step` driver also accepts gain overrides
on the command line, e.g. `--K_ip 0.5 --name kip05`, and `--no-feedforward`.

**Feedforward** — the step tests pre-settle with feedforward **off** (so the
reactive integral nulls Q to its target), then enable it for the recorded step.
`closed_loop_step` exposes `--no-feedforward` to run pure PI; `frequency_response`
is driven feedforward-on by the harness (it characterises the ff bandwidth).

**Frequency sweep** — `frequency_response/run.py` flags: `--mode {p,q,pq90}`,
`--freqs 0.1 0.2 …`, `--base-mw`, `--amp-mw`, `--base-mvar`, `--amp-mvar`,
`--duration`, `--settle`.

**Orchestration config** — `common/run_all_tests.py` has `PY`, `ROOT`, and
`FREQ_MODES` constants at the top (absolute paths for this machine); pass a
stack subset as CLI args to limit the run.
